# Завдання: harness для оцінки генерації RDDL локальною LLM

## Контекст

RDDL (Relational Dynamic Influence Diagram Language) — декларативна мова опису
факторизованих MDP/POMDP. `pyRDDLGym` парсить `.rddl` файли й будує з них
Gymnasium-сумісні середовища.

Мета проєкту: виміряти, наскільки добре локальна LLM (Gemma 4 12B QAT через
LM Studio) генерує коректні RDDL-домени з опису задачі природною мовою.
Вимірюємо трьома числами: частка валідних з першої спроби, частка валідних
після одного раунду з поверненням помилки, і розподіл першого провалу за
рівнями валідації.

Це дослідницький інструмент, не продукт. Пріоритет — прозорість і легкість
модифікації, не універсальність.

## Модулі

### extract.py

Витягує з відповіді моделі три RDDL-блоки: `domain`, `non-fluents`, `instance`.

- Блоки приходять у markdown code fences (```rddl ... ```), але модель може
  їх пропустити — передбач fallback на розбір голого тексту.
- Розпізнавай блок за першим значущим словом (`domain` / `non-fluents` /
  `instance`), а не за порядком.
- `pyRDDLGym` очікує ДВА файли: `domain.rddl` і `instance.rddl`, причому
  блоки `non-fluents` та `instance` мають бути в одному файлі. Склеюй їх.
- Якщо якогось блоку немає — це помилка рівня `extract`.

### lint.py

Статичні перевірки регулярками ДО виклику парсера. Причина існування рівня:
повідомлення парсера часто вказують позицію в токенах і мало допомагають
моделі при ремонті. Лінт формулює проблему так, щоб з неї було зрозуміло,
що саме правити.

Кожна перевірка повертає текст помилки англійською, придатний для прямої
вставки у feedback-повідомлення моделі.

Обов'язковий набір (це реальні помилки, зафіксовані на цій моделі):

1. Блок `non-fluents` не містить рядка `domain = <ім'я>;`
2. Блок `instance` не містить `domain = ...;` або `non-fluents = ...;`
3. Ім'я блоку `non-fluents` збігається з іменем домену
4. Крапка з комою після `}` блоків верхнього рівня (`};`)
5. Порядок секцій усередині `domain` відмінний від:
   requirements, types, pvariables, cpfs, reward, state-invariants,
   action-preconditions, termination
6. Агрегація (`sum_`, `prod_`, `avg_`, `min_`, `max_`, `forall_`, `exists_`)
   не обгорнута у власні `[...]` або `(...)`. Перевіряй символ безпосередньо
   перед агрегатором.
7. Штрих у ПРАВІЙ частині CPF (циклічна залежність)
8. Штрих поставлено після списку параметрів: `f(?x)'` замість `f'(?x)`
9. State-fluent без жодного CPF
10. Умова `if` без дужок: `if <expr> then` замість `if (<expr>) then`
11. У секції `non-fluents { }` присвоєно змінну, оголошену в `pvariables`
    як `state-fluent` (початковий стан має бути в `init-state`)
12. Блок `objects` порушує форму `<тип> : { обʼєкти }` — зокрема випадок,
    коли модель оголошує кожен об'єкт як окремий тип
13. Порожній блок `termination { };`
14. Відсутній блок `state-invariants` — попередження, не помилка: без нього
    pyRDDLGym не виведе box-межі й простори стануть (-inf, +inf)

Розділяй `errors` і `warnings`. Пункт 14 — warning, решта — errors.

### parse.py

Пише блоки у тимчасові файли, викликає `pyRDDLGym.make(domain=..., instance=...)`
у try/except, повертає або середовище, або текст винятку.

### simulate.py

Прогін випадкової політики (200 кроків за замовчуванням). Ловить:

- рантайм-виключення
- NaN або нескінченність у винагороді
- константну винагороду на всій траєкторії (ознака, що reward не залежить
  ні від стану, ні від дії — синтаксично валідно, семантично сміття)

### semantic.py

Перевірки під конкретну задачу. Реєстр `SEMANTIC_CHECKS: dict[str, Callable]`,
ключ збігається з іменем файлу задачі без розширення.

Для `shelves`:
- запас кожної полиці завжди в межах [0, 10]
- дія поповнення хоча б раз була доступна
- хоча б одна полиця за 300 кроків досягла нуля (інакше попит не віднімається)

Для `duel` поки залиш заглушку, яка нічого не перевіряє, — напишу пізніше.

### llm.py

Клієнт до LM Studio. OpenAI-сумісний endpoint, автентифікація не потрібна.

- URL за замовчуванням `http://localhost:1234/v1/chat/completions`,
  перевизначається через `--endpoint` або змінну оточення `LMSTUDIO_URL`
- модель за замовчуванням `google/gemma-4-12b-qat`, перевизначається через `--model`
- таймаут щедрий: 12B на 32k контексту генерує повільно, став 900 секунд
- обробляй помилки з'єднання з внятним повідомленням («сервер LM Studio
  недоступний за адресою X — перевірте, що Status: Running»)

### pipeline.py

Послідовність `extract → lint → parse → simulate → semantic`. Зупинка на
першому рівні, що дав помилки. Повертає назву рівня та список проблем.

Цикл ремонту: при провалі формує feedback-повідомлення зі списком проблем,
додає до історії діалогу пару (assistant: попередній вивід, user: feedback)
і повторює. Кількість раундів — параметр.

Системний промпт збирається як `system_prompt.txt` з підстановкою вмісту
`spec/rddl.rst` на місце плейсхолдера `{spec}`. Використовуй `str.replace`,
НЕ `str.format` і НЕ f-string: у промпті є фігурні дужки RDDL-синтаксису.

### cli.py

```
python -m rddl_eval \
    --task tasks/shelves.txt \
    --spec spec/rddl.rst \
    --runs 5 \
    --repairs 1 \
    --temperature 0.7 \
    [--endpoint URL] [--model NAME] [--out results/]
```

Вивід у stdout: по рядку на прогон з результатом і рівнем провалу, потім
підсумок — first-pass valid, valid after repair, розподіл першого провалу
за рівнями.

Кожен прогон також зберігається у `results/<timestamp>_<task>.json`: повний
діалог, усі проміжні виводи моделі, знайдені проблеми на кожному рівні.
Без цього неможливо потім розібратися, що саме пішло не так.

## Критично: перевір API pyRDDLGym

Я не впевнений у точних сигнатурах двох викликів. НЕ вгадуй — встанови пакет
і перевір фактично (`pip show pyrddlgym`, потім `help()` або читання джерел):

- `RandomAgent.__init__` — чи приймає `seed`
- `RandomAgent.sample_action` — чи приймає поточний стан аргументом

Також звір спосіб створення середовища та формат повернення `step()` з
документацією встановленої версії. API між 1.x і 2.x відрізнявся.

Якщо реальний API не збігається з описаним у цьому брифі — вір API,
а не брифу, і познач розбіжність у README.

## Тести

`tests/test_lint.py` має покривати кожну перевірку лінта окремим фікстур-файлом
у `fixtures/invalid/`, названим за номером правила. Плюс щонайменше один
завідомо коректний домен у `fixtures/valid/`, на якому лінт мовчить.

Тести лінта не повинні викликати ні LLM, ні pyRDDLGym — тільки регулярки.
Це має проганятися за секунду.

Окремо додай smoke-тест, що бере фікстуру з `fixtures/valid/` і проганяє її
через `parse` та `simulate`. Він вимагає pyRDDLGym, познач його маркером
pytest, щоб можна було пропустити.

## Приймальні критерії

1. `pytest` проходить без мережі та без запущеного LM Studio
2. Валідний домен із `fixtures/valid/` доходить до рівня `pass`
3. Кожна зламана фікстура ловиться саме тим правилом, під яке створена
4. Повний прогон із запущеним LM Studio завершується і друкує підсумок
5. README пояснює, як завантажити спеку, де взяти промпт, як запустити

## Чого НЕ робити

- Не вигадуй RDDL-синтаксис. Якщо сумніваєшся щодо правила — краще не додавай
  перевірку взагалі, ніж додаси хибну: хибний лінт зіпсує feedback моделі й
  спрямує її в неправильний бік.
- Не додавай веб-інтерфейс, дашборди, візуалізацію.
- Не абстрагуй під «підтримку різних провайдерів LLM». Один LM Studio.
- Не пиши семантичні перевірки для задач, яких немає в `tasks/`.
- Не роби автоматичний ретрай при мережевих помилках — краще впасти голосно.
